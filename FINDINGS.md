# Findings

This document records observed Unity Editor and Test Framework behavior, together with reliable design rules for UnityLeanMcp and similar tools that must operate across compilation, domain reloads, shutdowns, reconnects, and multiple desktop platforms.

## Domain reload and Editor lifecycle

- Unity's managed domain reload is asynchronous and can be triggered externally by script changes, compilation, package activity, Editor interaction, or shutdown. Every command must tolerate interruption and reinitialization at any point, including before its first callback or after its work has completed but before its response is delivered.
- Static fields, callbacks, background threads, sockets, and managed objects do not survive a domain reload. Persist the minimum operation identity and recovery state outside ordinary managed state before starting work that can reload the domain.
- `SessionState` survives a domain reload within the same Editor process but is reset when the process restarts. A persisted `SessionState` identifier can distinguish same-process reload recovery from an Editor restart.
- `AssemblyReloadEvents.beforeAssemblyReload` runs before the old domain is unloaded, but very little managed lifetime remains. Use it only for small, idempotent durable transitions and transport shutdown; never depend on a later old-domain callback.
- Register lifecycle callbacks again in every new domain. Registration and recovery must both be idempotent because initialization order and partially completed prior cleanup cannot be assumed.
- A reload and an Editor shutdown are interruption events, not ordinary command failures. Record an explicit interrupted outcome when possible, and do not silently convert either event into success.
- Socket-initiated Editor shutdown (`EXIT`) should stop listener services and invoke process exit (`EditorApplication.Exit(0)`) immediately rather than deferring exit across update ticks to wait for active operations. Unity's standard quitting lifecycle (`EditorApplication.quitting`) invokes interruption recovery handlers to mark any in-flight operations as interrupted in durable state cleanly and quickly.
- Unity may lock assembly reloads while tests are running. Script changes made during a test can be queued until the Test Framework releases that lock, so a test that edits a script does not necessarily exercise mid-test domain reload recovery.
- Stop Play Mode asynchronously and wait until both `EditorApplication.isPlaying` and `isPlayingOrWillChangePlaymode` are false before starting an operation that requires Edit Mode. Do not impose arbitrary bounded timeouts on Play Mode exit: the runner assumes Unity and project code will complete state transitions cleanly. If user scripts or modal prompts prevent Play Mode from exiting (e.g. `Application.wantsToQuit` returning `false`, modal dialogs, or infinite loops), that is external project-level behavior rather than an MCP runner defect. Operations must truthfully remain active until they finish, fail, or are explicitly stopped by the user (e.g. via `unity_stop` / process kill).

## Durable operations and interruption recovery

- Give every mutating request a unique client-generated operation ID. Include it in the start request, every poll, durable state, running marker, and terminal result.
- Serialize mutating operations through one project-scoped owner record. An identical operation ID is an idempotent retry; a different active ID must receive an explicit busy response instead of racing shared Unity or filesystem state.
- Make the operation lifecycle transactional: claim ownership, persist intent, begin Unity work, atomically persist the terminal result, then release ownership. Never clear ownership or a running marker before the result is durable.
- A command may finish inside Unity while its socket response is lost to reload. Retry only after a transport failure, and make the retry retrieve the existing correlated result rather than start the work again.
- Never delete or overwrite a marker/result unless its operation ID matches the caller. A stale callback, retry, or cleanup path must not mutate a newer operation's state.
- Recovery must use operation identities or generations. A callback from an older test run or domain must never overwrite state created by a newer request.
- Avoid deleting existing terminal result files (e.g., test/execute/eval result JSON) in-place at the beginning of an operation. Because clients match results by client-generated `operationId` and writers atomically replace results upon completion, in-place deletion is redundant and exposes transient 0-byte or `DELETE_PENDING` states to concurrent background readers on Windows NTFS.
- Polling handlers must evaluate operation state in strict hierarchical precedence: check the terminal result file for a matching client-generated operation ID first; if the result is absent or belongs to an older run, check the active running marker next; only if neither matches, query the durable operation journal for foreign ownership (yielding `BUSY`) or idle state. A poll handler must never return `IDLE` solely because an older terminal result file on disk failed to match the current operation ID, as this prematurely declares idle state while the newer operation is actively running.
- Reload and shutdown handling must be idempotent. Repeated lifecycle callbacks, duplicate Test Framework callbacks, or recovery after a partial cleanup must converge on one terminal outcome.
- A missing, unreadable, or malformed recovery record is not successful completion. Clear any in-memory snapshot, quarantine malformed data where practical, and report a recoverable error rather than guessing.
- In line-oriented socket protocols returning single-line status responses (e.g., `SUCCESS <payload>`), JSON serialization must be compact (`JsonUtility.ToJson(result, false)`). Emitting pretty-printed multi-line JSON in single-line responses causes socket line readers and shell scripts to capture only the opening brace (`{`), truncating the response. All command responses must adhere to strict single-line status framing (`SUCCESS <payload>` / `FAILURE <message>` / `INTERRUPTION <message>`) or dedicated terminal result file readers.
- Multi-line command inputs (such as dynamic `eval` C# code snippets or `executemethod` string parameters containing physical newlines) must be escaped across line-oriented socket protocols into single-line tokens (`\n`, `\r`, `\t`, `\\`, `\"`) and unescaped on the server before compilation or dispatch. Transmitting raw physical newlines breaks line-based stream framing, causing server readers (`ReadLine()`) to truncate the payload after the first line.
- Symmetric protocol encoding (`ProtocolCodec`): Line-oriented protocols sending payloads (like `SUCCESS <payload>`, `FAILURE <message>`, and `EVAL <opId> <code>`) must escape backslashes (`\\` -> `\\\\`) in addition to newlines (`\r`, `\n`) and tabs (`\t`). Failing to escape backslashes in line payloads corrupts path separators on Windows (e.g., `C:\new\read` being inadvertently unescaped into a newline followed by `ew` and a carriage return followed by `ead`). Token/parameter codecs must symmetrically escape and unescape `\\`, `\"`, `\r`, `\n`, `\t`, and command tokenizers must preserve escaped quotes (`\"`) and escaped backslashes (`\\`) during scanning so that trailing backslashes in quoted arguments (e.g. `"C:\\Path\\\\"`) do not escape closing delimiters.
- Reflected static method lookup must enforce strict parameter arity matching. If no method overload matches the exact number of passed arguments, resolution must return `null` immediately rather than fall back to an arbitrary overload of the same name. Loose fallback matching causes nondeterministic method selection and converts missing-method errors into confusing runtime parameter-mismatch exceptions.
- Command parameter parsing for arbitrary reflected static methods must support `Enum` (by name and integral value), `Nullable<T>`, `Guid`, `char`, and standard primitive/floating-point types with invariant culture (`CultureInfo.InvariantCulture`) before falling back to JSON deserialization. This allows invocations to interact natively with standard Unity APIs and custom Editor methods without requiring bespoke string-wrapper methods.
- Persist only simple, version-tolerant data such as operation ID, kind, status, Editor-session ID, and timestamps. Reconstruct observers and Unity objects in the new domain instead of serializing runtime objects.
- Subcommand frontends and tools must perform strict, fail-fast argument validation (e.g., rejecting unexpected arguments on zero-parameter commands like `stop`, `status`, and validating arguments for `refresh`, `eval`, `executemethod`, and test filters) before initiating socket connections or spawning background processes.
- Extensible operation lifecycle handlers (`IOperationLifecycleHandler`, `OperationLifecycleRegistry`): Decouple cancellation, domain-reload recovery, restart recovery, and shutdown handling from static command dispatchers using polymorphic lifecycle handlers registered by operation kind. This satisfies the Open-Closed Principle (OCP), ensuring new operation types can define custom cancellation mechanics and recovery behavior without modifying core server loops or switch statements.

## Threading and transport

- Unity APIs are main-thread-affine unless explicitly documented otherwise. This includes APIs that can look like utility code, such as Unity serialization. Dispatch command handlers to the Editor thread by default.
- Unity does not guarantee the execution order of `[InitializeOnLoad]` classes across assemblies. If a background thread (e.g. the socket server thread) accesses a static class before the Unity main thread executes its static constructor, the CLR runs that static constructor on the background thread. Calling main-thread-affine Unity APIs (`EditorUtility`, `SessionState`, `EditorApplication`, `Application.dataPath`) from a static constructor will throw a `UnityException` and permanently poison the type with a `TypeInitializationException` for the lifetime of that domain. Helper and path classes must eliminate static constructors and static field initializers, defaulting to neutral values and relying on explicit main-thread `EnsureInitialized()` methods invoked sequentially during startup.
- Enforce explicit main-thread service initialization before starting background listener threads. The TCP socket server must only begin accepting external connections after dependent main-thread state (`CommandHelper`, `UnityLeanMcpPaths`, `UnityLeanMcpOperationStore`, `UnityLeanMcpCompilationTracker`, `UnityLeanMcpDispatcher`, `RoslynCompilerHelper`, test callbacks) has completed initialization.
- Structure command handler dispatching polymorphically by execution target (e.g., `WorkerThread` for lock-free snapshot polling, `MainThread` for serialized Unity API execution, `EditModeOnly` for operations requiring asynchronous Play Mode exit) rather than using hardcoded type-checking in the server loop.
- Keep socket acceptance and transport waiting off the Unity main thread. Main-thread handlers must start asynchronous work and return control to the Editor quickly so compilation, updates, callbacks, and reload can proceed.
- A worker-thread poll is safe only when it reads immutable or synchronized plain managed snapshots and filesystem state. Do not let it call Unity APIs or deserialize through Unity while another domain transition may be occurring.
- Before reload or shutdown, stop the listener, signal all waiting request threads, and close every active client. A blocked socket thread must not delay domain teardown or emit a fabricated protocol error after shutdown begins.
- A broken connection is evidence of transport interruption, not evidence that the underlying Unity operation failed. The client should rediscover the endpoint and poll by operation ID.
- Avoid bounded timeouts. Never use arbitrary timeouts to cut off operations or wait for tasks to finish (including Unity startup, asset importing, compilation, and domain reloads). Execution flow must assume that external processes and Unity operate correctly and will complete state transitions cleanly. Delays should only be used when strictly necessary for reliability—not as operation timeouts, but as short delays to allow external operations or services to warm up and settle. If a backing process or operation remains active indefinitely, the runner (including MCP tools) must truthfully remain active until the backing work finishes, fails, or is stopped by the user.
- Failure detection must be deterministic rather than time-based. If an external process or operation fails, determine that failure through deterministic OS and filesystem checks (e.g., `Process.HasExited` for spawned processes, `!IsUnityRunning(out _)` via PID/lockfiles for existing instances, or log parsing for fatal compilation errors) rather than assuming failure because an elapsed timer expired. A live, functioning background process must never be killed solely because startup or compilation took longer than an arbitrary deadline.
- Worker-thread early rejection for mutating commands: Mutating commands declare `IsMutating` and `RequiresCompilationSettled` polymorphically via `ICommandHandler` (conforming to the Open-Closed Principle). When a command arrives at `UnityLeanMcpServer`, the worker thread inspects `handler.IsMutating` and checks `UnityLeanMcpOperationStore.ReadThreadSafeSnapshot()` before enqueuing to `UnityLeanMcpDispatcher`. This allows rejecting conflicting concurrent requests (`BUSY <kind> <opId>` or `BUSY compile`) immediately without hardcoded command name checks in the server dispatcher. This avoids enqueuing onto the main-thread dispatcher when the main thread is already occupied executing a synchronous operation (such as an in-progress `eval` or `execute_method`), which would otherwise cause main-thread deadlocks, TCP client timeouts, and queue pollution that corrupts subsequent operations.
- Do not run two integration suites against the same Unity project concurrently. They share the Editor, project lock, scripts, `Temp` protocol files, and generated fixtures, so concurrency invalidates test isolation and can corrupt teardown assumptions.

## Compilation, refresh, and diagnostics

- `AssetDatabase.Refresh()` and `CompilationPipeline.RequestScriptCompilation()` start asynchronous Editor work and may cause compilation, domain reload, or both. Persist the request before invoking them and resume observation in the next domain.
- `EditorApplication.isCompiling`, `EditorApplication.isUpdating`, and related flags are transient observations, not durable operation state. They can be false before work starts and briefly between lifecycle phases.
- Do not declare refresh complete on the first idle observation. Require the request flags to clear and observe a settled Editor on multiple update ticks so a not-yet-started compilation is not mistaken for completion.
- Compiler diagnostics must be captured at `CompilationPipeline.assemblyCompilationFinished`, before a possible reload. `compilationFinished` or a later Editor update may be too late for warnings from the old domain.
- Persist captured diagnostics atomically and preserve them when the next domain is resuming the same refresh/recompile operation. An empty new-domain static collection must not erase valid old-domain diagnostics.
- Compilation completion, diagnostic publication, and Editor settling are distinct moments. Produce the final command result only after the Editor settles, but capture each assembly's diagnostics as soon as Unity publishes them.
- Compiler warning availability and formatting vary across Unity and compiler versions. Integration tests should generate a deterministic warning known to exist on the pinned version and assert that warning, rather than depend on incidental Unity warnings.
- Stack-trace IL offsets can vary across compiler versions. Normalize only the unstable portion and scope normalization to the intended fixture; broad normalization can hide meaningful regressions in unrelated output.
- Mutating action handlers (`EXECUTE_METHOD`, `RUN_TESTS`, `EVAL`) must enforce active compilation guards (`IsCompiling || RefreshPending -> BUSY compile` and `ScriptCompilationFailed -> FAILURE Compilation failed`) before resolving methods, scheduling test jobs, or compiling dynamic code. Dispatching actions while the compiler or asset database is actively recompiling assemblies risks race conditions with domain unloading and produces transient reflection or type resolution errors.

## Unity Test Framework

- `TestRunnerApi.Execute()` is asynchronous. `IsRunActive()` can be false before `RunStarted` and at other lifecycle boundaries, so it must not be used alone to infer cancellation or completion.
- Test Framework callbacks are authoritative for normal start, completion, failure, and cancellation. Bind callbacks to the exact run ID and verify durable ownership before writing results.
- Do not destroy or unregister Test Framework objects owned by other tools. UnityLeanMcp should identify and clean up only the callback owner it created.
- A successful `CancelTestRun` return value means cancellation was accepted, not that a terminal callback is guaranteed. Some Unity/Test Framework versions can remain in `Cancelling`; cancellation handling needs a bounded interruption path and must not be the sole basis of a reload-resilience test.
- Avoid tests that invoke private Test Framework cancellation internals through reflection. They validate undocumented framework behavior, can hang indefinitely across versions, and do not prove UnityLeanMcp's interruption recovery.
- A test run may complete while the Editor is also reloading or shutting down. Write a terminal result only if the callback still owns that run, and let lifecycle recovery handle the otherwise interrupted transport.
- Test running state cleanup (e.g. removing active running markers like `unity_test_running.txt`) must be strictly ownership-aware and verify that the durable running marker matches the completing run ID before deletion. Blind marker deletions allow delayed or duplicate callbacks across domain reloads to erase a subsequent test run's active progress marker.

## Filesystem and cross-platform behavior

- Derive the project root from `Application.dataPath`, not `Directory.GetCurrentDirectory()`. User code, launchers, IDEs, and operating systems can supply or change an unrelated working directory.
- Write durable state and result files atomically using a uniquely named temporary file in the destination directory, then replace or move it into place. Same-directory writes avoid cross-volume rename behavior.
- On Windows (NTFS/Win32), `File.Replace` (`ReplaceFileW`) and `File.Delete` have mandatory file-locking and `DELETE_PENDING` semantics, unlike POSIX `rename(2)` / unlinking on macOS and Linux. Concurrent readers or polling probes can observe transient sharing violations (`IOException`) or 0-byte reads during replacement and deletion. Cross-platform atomic file writers should include a short retry loop with backoff to handle transient read locks.
- Atomic file writers (`WriteAtomic`) must never fail silently if retries are exhausted. If all retry attempts fail to replace or move the temporary file into place, `WriteAtomic` must throw an explicit `IOException` capturing the inner exception so callers detect failure deterministically rather than continuing with stale disk state.
- Keep protocol filenames project-scoped and avoid unresolved environment variables, shell-specific path assumptions, or case-sensitive comparisons. Test paths containing spaces and both slash conventions.
- Unity lockfiles are platform-dependent. They may be empty, expose no owner, disappear briefly during startup/reload, or remain stale after an abnormal termination. Treat them as supporting evidence, not authoritative liveness.
- Process-image scans are unreliable when multiple projects or Unity versions are open. Prefer a project-scoped handshake and verified endpoint. Never guess process ownership or fall back to returning an arbitrary first process (`processes[0]`) when multiple Unity instances are running. If a process cannot be deterministically proven to belong to the target project (via project-scoped PID file, verified lockfile owner, or command-line arguments), process lookup must return `null` and stop/kill operations must fail safely rather than risk killing an unrelated project or Editor window.
- Pin both the Unity version and revision in `ProjectVersion.txt`, and run compatibility tests against installed versions deliberately. Opening a project in a different version can rewrite project settings and change compiler/test output independently of UnityLeanMcp.
- Test Windows, Linux, and macOS behavior explicitly. File replacement, lockfiles, process discovery, socket teardown, line endings, executable lookup, and shell quoting all have platform-specific failure modes.
- Shell scripts across Linux, macOS, and Windows Git Bash must never declare function-only keywords such as `local` in top-level script scope. POSIX shell interpreters produce runtime syntax failures when encountering `local` outside function definitions during fallback execution paths.
- Windows locked assembly publishing: On Windows, when publishing a .NET assembly (e.g. `dotnet publish ... -o .../MCP~`) while the target DLL is held open by a running process (such as the IDE's language server or MCP host), `File.Copy` / `MoveFile` fails with sharing violation `MSB3021` / `MSB3026`. Because Windows allows renaming files that were opened with `FILE_SHARE_DELETE` (the standard for .NET CLR assembly loading), renaming the locked target DLL to `<name>.old` prior to publishing allows the build to succeed immediately without terminating the host process.
- Cross-platform path rooting and URI generation (`Path.IsPathRooted` quirks on Unix): In .NET on Unix-like environments (Linux, macOS), `Path.IsPathRooted` only returns `true` for paths starting with `/` (POSIX directory separator) and returns `false` for Windows-style rooted paths with drive letters (e.g. `C:\...` or `C:/...`). When code normalizes or converts paths into RFC 8089 URIs (`file:///...`), relying solely on `Path.IsPathRooted` on Linux causes Windows paths to be treated as relative, incorrectly prefixing them with the project root (e.g. `C:/Repo/C:/Repo/...`). Explicit cross-platform path rooting checks (`IsPathRootedCrossPlatform`) must check for drive letters (`[A-Za-z]:[\\/]`) and leading slashes/backslashes in addition to `Path.IsPathRooted` before combining paths, and path joining must defensively trim leading/trailing slashes to prevent duplicate path separators across OS boundary assumptions.

## Test and maintenance discipline

- Integration fixtures that modify project files must save the original bytes and restore them on success, failure, signal, and early exit. Cleanup should be ownership-aware and must never overwrite a user's concurrent edit.
- Keep full-suite execution single-owner, but use focused cases during debugging. Before starting a new run, confirm that no prior Unity/test process is still active.
- Generated Unity files and settings rewrites should be removed from the worktree after validation. Review `git status` and `git diff --check` so test artifacts, line-ending changes, and Unity migrations are not committed accidentally.
- Golden-output normalization should be narrowly targeted to known nondeterminism such as duration, project path, or a fixture-specific IL offset. Never normalize error categories, operation IDs, or other values that establish protocol correctness.
- Reliability tests should assert durable externally observable outcomes: exact operation correlation, atomic results, recovery after a lost connection, busy rejection, and successful continuation after a real domain reload.
- Mock socket servers in tests verifying multi-stage progress reporting must coordinate state progression with polling commands (such as advancing running state on `POLL_TESTS`) rather than using uncoordinated `Task.Delay` in background threads. Under variable CPU load or multi-core contention in CI containers, thread scheduling jitter can cause background delays to elapse faster or slower than client poll intervals, causing intermediate progress states to be overwritten before the polling client can observe them.
- **Isolating system process detection in unit tests**: `UnityProcessManager` discovers active Unity instances by checking `PidFile`, `UnityLockfile`, and fallback system-wide process queries (`GetUnityProcesses()`). If a developer or CI environment has a live Unity Editor running, querying system processes (`Process.GetProcessesByName("Unity")`) returns that live instance. If `FindProjectUnityPid()` naively assumes a single machine-wide process belongs to an unassociated target directory (such as an empty temp test folder without a lockfile), `IsUnityRunning` falsely returns `true`. Consequently, unit tests exercising startup failure paths (e.g. missing executable or unstarted process readiness) skip expected exceptions and enter indefinite readiness polling loops. Fallback process discovery without lockfile proof must never assume an unproven solitary OS process targets an arbitrary directory, and unit tests using mock project roots must configure `ProcessProvider = () => Array.Empty<Process>()` and bounded cancellation tokens.

## MCP structured responses and diagnostics

- When enhancing MCP tools to provide structured, machine-readable payloads, maintain backward compatibility for existing consumers and test frameworks by keeping `result.Content[0]` as the human-readable `TextContentBlock` and appending `result.Content[1]` as the JSON-serialized structured model. MCP clients that concatenate text content blocks continue to match expected strings without disruption.
- Unity stack traces across Mono runtime, .NET Core runtime, and Unity Editor use varying line formats (`at ... [0x...] in <file>:<line>`, `at ... in <file>:line <line>`, and `... (at <file>:<line>)`). Robust source-location extraction must accommodate all three formats and filter out internal framework frames (such as `<filename unknown>:0` from NUnit assertion delegates) to locate actual user test code.
- Formatting source locations with standard markdown links (`[FilePath:Line](file:///AbsolutePath#LLine)`) allows autonomous agents, terminal emulators, and IDEs to provide direct one-click navigation to failing assertions.
- Eliminating metadata fluff and token overhead in lightweight inspection tools (`unity_status`): Simple inspection queries intended for agent situational awareness should return concise, unambiguous state tokens (`Ready`, `Not Running`, `Compiling`, `Running Unreachable`, `Busy (<op>)`) as a single text block rather than verbose diagnostic dumps (PID, Port, Mode, Editor Version, Project Root, timestamps) or duplicate JSON payloads. Eliminating redundant text fields and secondary JSON serialization minimizes conversational context consumption and prevents LLM distraction while remaining immediately interpretable.
- Unified compiler diagnostic formatting, warning capping, and error placement (`DiagnosticFormatter`, `unity_refresh`, `unity_run_tests`, `unity_eval`):
  - In projects containing third-party assets with obsolete APIs (`CS0618`), dumping raw compilation messages into tool responses causes token blowouts (2,000–5,000 tokens) that drown out actionable errors.
  - Capping warnings at a centralized limit (10) with an omission summary notice (`... and X more warning(s) omitted to preserve context window.`) when exceeding the limit, while suppressing the omission notice when warnings are within the cap (<= 10), preserves conversational context window headroom.
  - Always displaying warnings first and placing unfiltered compilation errors at the end of the message ensures the critical blocking failures appear adjacent to the tool boundary and receive maximum LLM recency attention.
  - Formatting file locations with direct RFC 8089 URIs (`• file:///AbsolutePath#LLine: error/warning CODE: msg`) resolves both project-relative and absolute paths across Windows and POSIX environments (`file:///C:/...` vs `file:///...`), providing unambiguous absolute path consumption and line navigation for AI agent inspection tools (`view_file`) while saving tokens by avoiding redundant markdown link syntax (`[path:line](...)`).
  - Emitting category headers (`Warnings:` and `Errors:`) only when both categories are present minimizes tokens on single-category outputs while providing clean visual and semantic separation when both exist.
- **Protocol status prefix stripping on immediate socket responses**: Line-oriented socket protocols emit single-line status framing tokens (`FAILURE <msg>`, `ERROR: <msg>`) to signal operation failure. When operations fail synchronously upon initial dispatch (e.g. `unity_eval` failing Roslyn snippet compilation), client handlers must strip the status token prefix (`StripStatusPrefix`) before unescaping and returning `result.Message`. Failing to strip the status token leaks protocol wire artifacts into the message payload, causing regex-based compiler diagnostic parsers (`s_CompilerDiagnosticRegex`) to misinterpret `"FAILURE eval"` as the file location and generate corrupt file URIs (`file:///.../FAILURE eval#L1`). Stripping the prefix symmetrically across both initial synchronous responses (`UnityClient`) and asynchronous polling responses (`OperationPoller`) preserves clean diagnostic parsing without requiring disk-based sidechannel file reads.

## Dynamic in-memory evaluation and object inspection

- In Unity projects, package-modular assemblies such as `UnityEngine.UI.dll` and `UnityEngine.UI` / `UnityEngine.EventSystems` (from `com.unity.ugui`) may not be installed or loaded in minimalist (headless, server, or VR) environments. Emitting unconditional `using` directives in dynamically compiled Roslyn evaluation wrappers will cause Roslyn compilation failure `CS0234` when those packages are omitted. Dynamic code generation must conditionally probe `AppDomain` assembly metadata (e.g. via `CommandHelper.FindType`) before emitting `using` statements for optional package namespaces.
- Unity `Transform` inherits from `Component`. In hierarchical type matchers like `CommandHelper.FormatResult`, specialized formatters for `Transform` must precede generic `Component` checks; otherwise, `Transform` instances are captured by the generic `Component on "<go>"` formatter.
- In cross-platform string formatting for MCP tool results, avoid hardcoded `\n` when joining lines with `StringBuilder.AppendLine()`. On Windows, `AppendLine()` uses `\r\n`, so mixing with `\n` causes inconsistent line endings across platforms. Consistently use `Environment.NewLine`.
- In dynamic in-memory evaluation (`EvalHandler.TryCompileSnippet`), speculative multi-pass compilation (trying expression wrapping `return (...)`, statement execution, and `; return null;`) and regex heuristics (`ExplicitReturnRegex`) were fragile, modified user code, and required up to three compilation attempts per snippet. By requiring explicit returns (`return <value>;`) when a return value is desired by the AI tool while allowing void snippets to exit naturally or with `return;`, the evaluator compiles code verbatim without any mutation or semicolon injection in a single compilation pass.
- Single-pass AST-based classification via Roslyn reflection (<0.05ms): Wrapping the code snippet in a lightweight probe method (`class __Probe { async Task<object> M() { <code> } }`) and parsing its syntax tree deterministically identifies whether the snippet contains a top-level return statement with an expression (`ReturnStatementSyntax.Expression != null`). Returns inside lambdas (`SimpleLambdaExpressionSyntax`, `ParenthesizedLambdaExpressionSyntax`, `AnonymousMethodExpressionSyntax`) or local functions/nested methods are ignored by verifying the ancestor chain up to probe method `M`.
- Roslyn dynamic reflection quirks: When Roslyn APIs are invoked via reflection across Unity Editor versions:
  - `CSharpSyntaxTree.GetRoot` takes an optional parameter: `GetRoot(CancellationToken cancellationToken = default)`. Looking up with parameter count 0 (`new Type[0]`) returns `null`. Invocation must explicitly match `GetRoot(CancellationToken)` and pass `default(CancellationToken)`.
  - `SyntaxNode.DescendantNodes` has multiple overloads, including `DescendantNodes(Func<SyntaxNode, bool>, bool)` (2 parameters) and `DescendantNodes(TextSpan, ...)` (3 parameters). Loose reflection searches that match any method named `DescendantNodes` can latch onto the 3-parameter overload; initializing the first parameter with `Activator.CreateInstance(typeof(TextSpan))` passes an empty span `[0..0)`, resulting in zero traversed nodes. Reflection must strictly target the 2-parameter overload and pass `new object[] { null, false }`.
- Supporting multiline C# source files and `using` directives in dynamic evaluation (`RoslynCompilerHelper.ExtractUsingDirectives`):
  When users or AI tools provide standard C# source text with `using` directives at the top (e.g. `using System.IO;`, `using static System.Math;`, `using IO = System.IO;`), placing them directly into a generated runner method body causes Roslyn compilation failure `CS1529: A using directive must precede all other elements defined in the namespace`.
  Extracting `UsingDirectiveSyntax` nodes via Roslyn AST reflection (with a line-based regex fallback) and hoisting them to file scope before the runner class solves this. Crucially, blanking out the extracted directive characters with spaces rather than deleting them preserves original line breaks (`\r\n`), ensuring that compiler error line and column numbers remain 1:1 identical to the caller's source code.
  Furthermore, distinguishing `UsingDirectiveSyntax` from `UsingStatementSyntax` (`using (var x = ...)`) and `LocalDeclarationStatementSyntax` (`using var x = ...`) guarantees disposable resource blocks remain inside the method body. Defensively unwrapping JSON-encoded input strings (e.g. `{"code": "..."}`) in `UnityTools.UnwrapJsonCodeIfPresent` prevents syntax errors when LLM agents mistakenly format the parameter as JSON.
- Eliminating implicit/default `using` statements in dynamic evaluation:
  Relying on implicit default `using` statements (such as `using UnityEngine;`, `using System.IO;`, `using UnityEngine.UI;`) introduced ambiguity, hidden dependencies, and subtle namespace collisions (e.g. `System.Diagnostics.Debug` vs `UnityEngine.Debug`, `System.Random` vs `UnityEngine.Random`, or UI package availability quirks). Removing all implicit default `using` directives and requiring callers / AI models to explicitly provide whatever `using` directives they need makes snippet evaluation completely deterministic and transparent.
  To ensure the generated wrapper class compiles reliably even when zero `using` statements are provided (e.g. primitive arithmetic `return 1 + 1;`), the runner method signature must use fully qualified types (`public static async System.Threading.Tasks.Task<object> Execute(System.Threading.CancellationToken cancellationToken)`).
- Disambiguating void statements vs. null returns in `unity_eval`: When dynamic code snippets do not include a return statement and produce no console logs, returning an explicit and actionable message (`"(Evaluation completed without a return statement. Use 'return <expr>;' to return a value.)"`) prevents agents from confusing void execution with a `null` result. Conversely, code snippets that explicitly return null (`return null;`) produce payload `"null"` and output `"null"`, clearly distinguishing void execution from returning a null reference.
- **Synthetic eval source location formatting and trailer disambiguation**: Dynamic in-memory Roslyn compilation injects directive `#line 1 "eval"` so diagnostic line numbers match user-submitted code lines. When formatting compiler errors, naive URI builders treat `"eval"` as a relative path and prepend the project root, hallucinating non-existent file URIs (`file:///.../eval#L1`) that trigger secondary "File not found" agent errors. When formatting eval diagnostics (`isEval: true`), synthetic identifiers (`eval`, `snippet`, `<...>`) must be formatted directly as `snippet line X, col Y:` without file URIs, while genuine project script diagnostics retain RFC 8089 `file:///` URIs. Furthermore, evaluating whether diagnostics originate from snippet code vs pre-refresh project scripts allows emitting distinct failure trailers (`Evaluation aborted: Dynamic snippet compilation failed.` vs `Evaluation aborted: Project script compilation failed.`), immediately directing agent attention to either the dynamic query or broken project source files.


## Agent operational context and MCP tool sequencing

- AI coding agents interacting with Unity via MCP rely heavily on tool descriptions to plan execution sequences and evaluate operational overhead. Without explicit operational context, agents frequently adopt inefficient behavioral patterns:
  - Redundant sequential pre-refreshing: Agents frequently call `unity_refresh` immediately prior to calling `unity_run_tests` or `unity_eval`, unaware that execution tools already perform an automated pre-refresh check. This burns unnecessary LLM reasoning turns, re-reads conversational context, and introduces needless round-trip latency. Unifying auto-refresh across all tools (`unity_run_tests` and `unity_eval`), setting MCP `ServerInstructions` in `Program.cs`, and explicitly instructing agents in tool descriptions not to invoke `unity_refresh` beforehand prevents these redundant calls entirely.
  - Consolidating execution into `unity_eval` and retiring `unity_execute_method`: Exposing both `unity_eval` and `unity_execute_method` on the MCP surface introduced unnecessary prompt token overhead (~120 tokens per turn) and agent decision friction ("should I call a static method or eval?"). Because `unity_eval` is a strict superset capable of calling static methods, inspecting GameObjects, and running expressions with complex types, `unity_execute_method` was redundant. In the rare event an agent needs to invoke private/internal static members, standard reflection can be executed inside `unity_eval`. Funneling all C# execution through `unity_eval` establishes a single, unambiguous tool for LLMs.
  - Hesitation to verify compilation health: Agents may avoid running compilation checks after code modifications when they fear `unity_refresh` is a heavyweight or domain-reloading operation. Clarifying that `unity_refresh` is fast (<200ms when unchanged) encourages agents to proactively check compiler diagnostics after edits when not immediately invoking an execution tool.
  - Clean rebuild vs. routine refresh: Merging the clean rebuild capability into `unity_refresh` via an optional `clean: bool = false` flag reduces the top-level MCP tool surface while avoiding agent hesitation. Crucially, naming this flag `clean` rather than `recompile` prevents agents from misinterpreting `clean: false` as "do not compile code" and avoids accidental invocation of expensive cache-clearing rebuilds on routine code edits.
  - Retiring `unity_status` and eliminating pre-flight turns: Autonomous agents frequently waste unnecessary reasoning turns calling `unity_status` before every action, burning context tokens and introducing round-trip latency. Because all mutating operations (`unity_refresh`, `unity_eval`, `unity_run_tests`) already auto-start Unity when not running and handle Editor busy states transparently, `unity_status` is redundant on the MCP surface. Retiring `unity_status` from the public MCP tool catalog reduces prompt overhead and agent pre-flight friction while preserving `IUnityClient.GetStatusAsync` internally for testing and status inspection.
  - Tiered autowaiting for Unity busy states:
    - **Transient compilation and lifecycle states**: When Unity is busy compiling, refreshing, or updating (`BUSY compile`, `COMPILING`, `UPDATING`, `BUSY refresh ...`, `BUSY recompile ...`), tools should not fail fast. Instead, they autowait without arbitrary bounded timeouts until compilation finishes and the Editor settles, streaming periodic MCP progress notifications (`progress?.Report(...)`) to keep the MCP client transport informed.
    - **Active foreign mutating operations**: When an operation encounters an active foreign operation (`BUSY <kind> <opId>` for `test`, `eval`, `execute`), the client observes a short grace period (3 seconds) to allow naturally completing operations to finish. If the foreign operation remains active after the grace period, the tool fails fast with an explicit, actionable diagnostic: `$"Unity is busy executing '{kind}' (id: {opId}). If this operation is hung, call unity_stop to recover."` This prevents deadlocks while giving the agent an immediate recovery path via `unity_stop`.
    - **Refresh/recompile polling priority (`PollRefreshHandler`)**: When checking operation state in `PollRefreshHandler`, active refresh and recompile operations must take precedence over operation ID matching (`operation.kind == Refresh || operation.kind == Recompile`), returning `COMPILING` rather than `BUSY refresh <opId>`. This ensures callers polling for compilation completion observe uniform `COMPILING` status across domain reloads and assembly updates.
  - MCP client-side tool execution timeouts: Even when UnityLeanMcp tools avoid bounded timeouts and poll indefinitely, MCP clients (such as Codex CLI, Claude Code, or Cursor) enforce client-side execution timeouts on `tools/call` JSON-RPC requests (defaulting to 60s or 300s). For long-running operations like large test suites or heavy compilation, client-side configuration (such as `tool_timeout_sec = 1800` in `.codex/config.toml`) must be explicitly configured to prevent clients from prematurely aborting with `timed out awaiting tools/call after 300s`.
  - Interactive GUI Editor termination protection in `unity_stop` (`force` safety guard): When developers work interactively with the Unity GUI Editor open, an AI agent invoking `unity_stop` (e.g. attempting to recover from what it perceives as a hang or trying to release project locks) would abruptly terminate the user's interactive Editor process, risking the loss of unsaved scene modifications, open inspector edits, or active play sessions. By checking `GetUnityMode(pid)` and refusing to terminate when running in `GUI` mode unless `force: true` is explicitly provided, `unity_stop` provides a vital safety guard that returns an informative error (`"Refusing to stop Unity: The active Unity Editor is running in interactive GUI mode. Stopping it may lose unsaved user changes. Set 'force: true' to stop it anyway."`) while preserving the ability to force termination when deliberately intended.

## Editor architecture and utility decomposition

- Decomposing monolithic editor utilities (like `CommandHelper`) into single-responsibility classes (`CommandLineTokenizer`, `ParameterTypeConverter`, `UnityResultFormatter`, `MethodResolver`) keeps domain logic cohesive, easily testable, and isolated. Backward-compatible one-line forwarding stubs on the original utility class ensure existing internal and external callers continue to function without disruption.
- Decomposing MCP client and process management orchestrators (`UnityClient`, `UnityProcessManager`): Monolithic runner and client classes tend to accumulate disparate cross-cutting concerns over time: low-level TCP loopback stream transport, regex compilation log extraction, file-based polling state machines, and cancellation mechanics. Extracting these concerns into focused single-responsibility services (`UnitySocketTransport` for TCP socket communication and probing, `UnityLogScanner` for regex compilation error extraction and log snippets, and `OperationPoller` for polling state machines and cancellation) satisfies the Single Responsibility Principle (SRP) while drastically reducing class complexity. Backward compatibility with existing dependency injection graphs, test fakes (`FakeUnityClient`, `FakeUnityProcessManager`), and unit test call sites is preserved by providing default-instantiating constructor overloads and forwarding helpers.
- Purging unused structured models and formalizing method deprecation (`Models.cs`, `IUnityClient`): Experimental response models designed for secondary JSON payloads (`StructuredRefreshResult`, `StructuredEvalResult`, `StructuredTestRunResult`) that are never instantiated or returned add dead code bloat and cognitive friction when developers inspect public contracts. Removing unused models while retaining actively consumed types (`StructuredCompilerDiagnostic`, `StructuredTestFailure` for diagnostics formatting) maintains lean contracts. Concurrently, marking retired interface methods like `ExecuteMethodAsync` with `[Obsolete("unity_execute_method has been retired; use EvalAsync instead.")]` preserves backward compatibility with existing tests while clearly guiding developers toward canonical tools (`unity_eval`).

## Operation-scoped result files and elimination of Win32 NTFS sharing collisions (Issue #87)

- **Elimination of `ReplaceFileW` locking collisions via operation-scoped files**:
  - Previously, all operations shared static destination files (`Temp/unity_eval_result.json`, `Temp/unity_test_results.json`, `Temp/unity_execute_result.json`). Overwriting an existing destination required `WriteAtomic` to call `File.Replace(tempPath, targetPath, null)` (backed by Win32 `ReplaceFileW`).
  - On Windows NTFS, `ReplaceFileW` requires exclusive access to the destination file. If a reader (such as `PollHelper` or `OperationPoller`) had the file open even with `FileShare.ReadWrite`, `ReplaceFileW` failed with `ERROR_SHARING_VIOLATION`.
  - Switching to operation-scoped result files (`Temp/unity_eval_<operationId>.json`, `Temp/unity_execute_<operationId>.json`, `Temp/unity_test_<operationId>.json`) eliminates `File.Replace` entirely. Because each operation generates a fresh ID, the destination file never exists beforehand. `WriteAtomic` moves the temporary file directly into place via `File.Move(tempPath, targetPath)`. `File.Move` to an uncreated target path avoids `ReplaceFileW`, requires no exclusive replacement locks, and executes atomically across Windows, Linux, and macOS.
- **Strict adherence to Rule 21 ("Never clear ownership before result is durable")**:
  - In `OperationExecutionEngine.FinishOperation` and `MarkInterrupted`, `UnityLeanMcpOperationStore.Complete(operationId)` must only execute inside the `try` block after `WriteAtomic` has completed without throwing. Clearing ownership in a `finally` block or before `WriteAtomic` finishes causes false-positive `IDLE` reporting if writing fails or encounters a transient issue.
- **Boundary race condition between result persistence and ownership release**:
  - In `PollHelper`, polling worker threads evaluate terminal results before checking the durable operation store snapshot. When an operation finishes on Unity's main thread, `FinishOperation` writes the result file and then calls `UnityLeanMcpOperationStore.Complete(operationId)` to delete `unity_operation.json`.
  - If a worker-thread poll checks the result file right before `File.Move` completes, and subsequently checks the operation store right after `Complete(operationId)` deletes the journal, it observed neither a result file nor an active operation, falsely outputting `IDLE`.
  - Re-checking the terminal result file inside `PollHelper` when `operation == null` before emitting `IDLE` eliminates this boundary race condition inside the Editor.
  - Concurrently, allowing a brief settlement retry loop (up to 200ms across 5 attempts) in `OperationPoller` before declaring IDLE failure accommodates Windows NTFS directory attribute cache settlement across processes.
- **Preserving persistent test failure history for `--failed-only` re-runs**:
  - While client-correlated test results are written to `Temp/unity_test_<runId>.json` and cleaned up by the client upon terminal read, Unity's `--failed-only` test re-runner (`RunTestsHandler.GetPreviouslyFailedTestNames()`) inspects `unity_test_results.json` to identify which tests previously failed.
  - `MyTestCallbacks.FinalizeTestRun` persists the authoritative results to both the operation-scoped path (`RunTestsHandler.GetResultsFilePath(runId)`) for client polling and `RunTestsHandler.ResultsFilePath` (`unity_test_results.json`) for Editor history. Because the client only polls and deletes the operation-scoped file, `unity_test_results.json` remains persistent for `--failed-only` runs without lock contention.

## Test suite performance, domain-reload avoidance, and client session reuse

- **Static test fixtures vs. dynamic file swapping**: Dynamically mutating project files (`Assets/Tests/Editor/DummyTest.cs`) during integration tests forces Unity to trigger full asset re-indexing, script recompilation, and managed domain reloads (2–4 seconds per cycle). Running setup and teardown file copies for every test case introduces double domain reloads per test. Replacing dynamic file swapping with statically compiled test classes (`DummyTest.cs` and `DummyExecuteClass.cs`) and leveraging NUnit test filters (`filter = "..."`), categories (`category = "..."`), and `[Explicit]` attributes allows the entire test framework suite to execute against pre-compiled assemblies in milliseconds without triggering a single domain reload.
- **Persistent MCP client session reuse**: Spawning a new OS child process (`dotnet UnityLeanMcp.Mcp.dll`) for every test method incurs hundreds of milliseconds of .NET CLR initialization, pipe creation, and JSON-RPC handshake overhead. Reusing a single `McpTestClient` session per test fixture (or collection) mirrors production MCP clients (Claude Code, Cursor, Codex) that maintain persistent stdio sessions across multiple tool invocations. This provides superior test safety by verifying that the server handles repeated requests without socket leaks, queue corruption, or memory leaks while cutting suite runtime significantly.
- **Configurable busy grace periods in testing**: Hardcoded operation grace periods (e.g. 3 seconds waiting for foreign operations to settle) force mock-socket unit tests to idle needlessly. Exposing `BusyGracePeriod` on `UnityClient` allows unit and subsystem tests to inject sub-100ms grace periods, verifying fail-fast diagnostics and retry policies deterministically in milliseconds without sacrificing production default safety.
- **Three-tier test categorization via xUnit traits**: Partitioning tests into `Category=Unit` (pure C# logic, codecs, formatters, path resolution), `Category=Subsystem` (mock loopback TCP servers verifying protocols, tiered autowaiting, and cancellations without Unity), and `Category=UnityIntegration` (live Unity Editor smoke tests) enables an instant sub-3-second local developer feedback loop (`dotnet test --filter "Category!=UnityIntegration"`) while preserving complete end-to-end safety in CI.

## Unity Test Framework filter mechanics and error reporting (Issue #91)

- **`Filter` parameter semantics in Unity Test Framework**:
  - `Filter.groupNames` strictly evaluates inputs as .NET Regular Expressions (`FullNameFilter { IsRegex = true }`).
  - Passing glob patterns (e.g. `*Movement*`) directly into `groupNames` causes a .NET regex compilation exception (`Quantifier * following nothing`) in the Editor before any test execution starts.
  - `Filter.testNames` performs exact string matching against full test names (`Namespace.Class.MethodName`), evaluated via string equality (`FullNameFilter { IsRegex = false }`). Test names cannot be regex patterns or method-only substrings.
  - `Filter.assemblyNames` filters test fixtures by target assembly name (e.g. `MyProject.Tests`).
  - `Filter.categoryNames` filters tests decorated with NUnit's `[Category("...")]` attribute.
  - Subcommand frontends and MCP tools must pass filter parameters verbatim without lossy heuristic translations (such as silently translating `*` to `.*`), allowing users and AI agents to leverage Unity's native regex semantics deterministically.
- **Support both single strings and arrays across all filter parameters**:
  - AI agents and tool callers frequently pass either a single string (e.g. `testName: "MyTest"`, `group: "MyRegex"`) or an array of strings (`testNames: ["Test1", "Test2"]`, `groupNames: ["Regex1", "Regex2"]`).
  - Providing dual-accepting parameter signatures (`testName` / `testNames`, `group` / `groupNames`, `category` / `categoryNames`, `assembly` / `assemblyNames`, plus legacy `filter`) combined into clean arrays ensures robust ergonomics for agents without brittle type coercion failures.
- **Error masking trap when test runs fail before execution**:
  - When Unity Test Framework aborts early due to invalid regex syntax in `groupNames`, assembly compilation errors, or test runner exceptions, `totalTests` is 0 and `Success` is `false` with a diagnostic message.
  - If client-side result formatting checks `hasAnyFilter && totalTests == 0` prior to checking `!result.Success && !string.IsNullOrWhiteSpace(result.Message)`, it falsely reports `"No tests found matching filter..."`. This completely masks the true underlying exception from the developer or AI agent, misleading them into believing their test names were wrong rather than detecting a broken regex or runner failure.
  - Formatting and reporting logic must always prioritize surfacing `!result.Success` errors over zero-count filter messages.
